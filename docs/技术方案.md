## 1. 产品范围与设计约束

### 1.1 核心命题

四个模块不是四个独立工具的拼装，而是**一条数据链**：

```
目标(Goal) ──拆解──> 待办(Task) ──排期──> 日历(Event)
   │                     │                    │
   └──────── 引用 ───── 笔记(Note) ───────────┘
                          │
                    聚合 ▼
                    复盘(Review)
```

「整合」的技术含义是：**跨实体的双向链接 + 一份 append-only 的行为日志**。没有这两样，四个模块就只是并列的四个 CRUD。

### 1.2 硬性约束

| 约束 | 说明 |
|---|---|
| 本地优先 | 所有数据落在本机 SQLite，无网络也 100% 可用。不做云端依赖。 |
| Markdown 为文本格式 | 笔记正文、任务备注、目标描述、复盘正文一律 Markdown 字符串。 |
| 动效密度高但克制 | 参考 Telegram：动画多，但每个都短（120–320ms）、可打断、只跑合成器。 |
| 中文优先 | 中文分词搜索、中文排版、IME 输入不能有任何卡顿或吞字。 |
| 单人可维护 | 不引入需要专职维护的基础设施。 |

### 1.3 明确不做（v1）

- 多设备同步、协作、分享
- 移动端（但数据模型为其预留，见 [5.1](#51-存储决策)）
- 插件系统
- AI 功能

## 3. 架构总览

### 3.1 进程与线程模型

```
┌─────────────────────────────────────────────────────────┐
│ WebView 进程 (WebView2 / WKWebView)                      │
│                                                          │
│  主线程                        合成线程 (GPU)             │
│  ├─ React 渲染                 └─ transform / opacity     │
│  ├─ Motion 动画驱动                动画在这里跑，          │
│  ├─ Milkdown / ProseMirror         主线程卡了也不掉帧      │
│  └─ TanStack Query 缓存                                   │
│                                                          │
│  Web Worker                                              │
│  └─ 大文档 Markdown 预解析、导出渲染                       │
└───────────────────────┬─────────────────────────────────┘
                        │ Tauri IPC（JSON，往返 ~1–3ms）
┌───────────────────────┴─────────────────────────────────┐
│ Rust 主进程                                              │
│                                                          │
│  async runtime (tokio)                                   │
│  └─ #[tauri::command] → spawn_blocking → r2d2 池          │
│                                                          │
│  阻塞线程池                                               │
│  ├─ SQLite 读写（WAL：多读单写并发）                       │
│  ├─ jieba 分词                                            │
│  ├─ rrule 重复规则展开                                     │
│  └─ 全库导出 / 备份                                        │
│                                                          │
│  后台任务                                                 │
│  ├─ 提醒调度器（tokio interval，每 30s 扫一次）             │
│  └─ 自动备份（每日一次 SQLite Online Backup）              │
└─────────────────────────────────────────────────────────┘
```

**铁律：任何可能超过 1ms 的计算都不留在 WebView 主线程。**
分词、搜索、重复规则展开、统计聚合、导出 —— 全部 Rust。前端只负责渲染和动画。

### 3.2 数据流

```
用户操作
   │
   ├─► Zustand（纯 UI 状态：面板开合、选中项、拖拽中）——同步，0 延迟
   │
   └─► TanStack Query mutation
          │
          ├─► onMutate: 乐观更新缓存 ──► UI 立即变化 + 动画启动
          │
          ├─► invoke('task_complete', ...) ──► Rust ──► SQLite
          │                                        └──► activity 日志
          │
          ├─► onError: 回滚缓存 + 抖动动画提示
          └─► onSettled: 精确失效相关 query key
```

> **乐观更新不是优化，是必需品。**
> IPC 往返 1–3ms，但「写库 + 重查询 + React 重渲染」的完整链路是 15–40ms。动画一旦要等这个链路，起手就慢半拍，手感立刻从「Telegram 级」掉到「网页级」。所有 mutation 一律先改缓存再发 IPC。

## 5. 数据层设计

### 5.1 存储决策

**SQLite 是唯一真相来源**，笔记正文以 Markdown 字符串存在字段里。

理由：四个模块强关联（任务挂目标、笔记引用日程、复盘聚合全部数据），关系型存储天然合适。纯文件方案（Obsidian 式）会引入文件监听、外部修改冲突、原子性缺失三个长期问题，收益只有「可以用别的编辑器打开」。

代价与补偿：提供**「导出为 Markdown 文件夹」**功能（带 front-matter），让用户随时能拿走数据。这满足了数据主权诉求，又不用承担文件同步的复杂度。

**为未来的多设备同步预留（现在不实现）：**

1. 所有主键用 **UUIDv7**（时间有序，索引局部性好，且天然无冲突）
2. **软删除**：`deleted_at INTEGER NULL`，永不物理删除（清理由用户手动触发）
3. 每张表都有 `updated_at INTEGER NOT NULL`（UTC ms）
4. 不使用 `AUTOINCREMENT` 主键（`activity` 表除外，它是纯本地日志）

做到这四点，将来接 CRDT（Automerge / cr-sqlite）的成本从「重构」降到「加一层」。

### 5.2 时间与时区约定

> 日历应用最容易翻车的地方。以下约定强制执行，任何例外都要在代码里写明理由。

| 场景 | 存储方式 | 类型 |
|---|---|---|
| 记录型时间戳（created_at / updated_at / completed_at） | UTC 毫秒 | `INTEGER` |
| **定时**事件、定时提醒 | UTC 毫秒 + 独立的 IANA 时区字段 | `INTEGER` + `TEXT` |
| **全天**事件、任务截止日（全天） | 本地日期字符串 `'YYYY-MM-DD'` | `TEXT` |
| 复盘周期起点 | 本地日期字符串 `'YYYY-MM-DD'` | `TEXT` |

**为什么全天事件必须存字符串**：「10 月 1 日国庆」在任何时区都是 10 月 1 日。如果存成 UTC 毫秒，用户从北京飞到纽约，节日会显示成 9 月 30 日。

**为什么定时事件要额外存 `tz`**：重复规则必须在**事件原始时区**里展开。「每周一早 9 点」跨越夏令时后，UTC 时刻会变，但本地 9 点不变。只有保留 `tz` 才能正确展开。

前端时间运算**全部经过 `src/lib/date.ts`**，内部用 Temporal（`temporal-polyfill`）。禁止在业务代码里直接 `new Date()` 做加减 —— Date 的月份加法、时区处理坑太多。

### 5.3 表结构

`src-tauri/migrations/0001_init.sql`：

```sql
-- ============ 连接级配置（每次开连接都要执行，见 db/pragma.rs） ============
-- PRAGMA journal_mode = WAL;        -- 多读单写并发；只需设置一次，持久化在库文件里
-- PRAGMA synchronous  = NORMAL;     -- WAL 下足够安全，比 FULL 快一个数量级
-- PRAGMA foreign_keys = ON;         -- 每个连接都要设，默认是关的
-- PRAGMA busy_timeout = 5000;
-- PRAGMA temp_store   = MEMORY;
-- PRAGMA mmap_size    = 268435456;  -- 256MB

-- ============================== 笔记 ==============================
CREATE TABLE note (
  id             TEXT    PRIMARY KEY,               -- UUIDv7
  title          TEXT    NOT NULL DEFAULT '',
  content_md     TEXT    NOT NULL DEFAULT '',
  content_tokens TEXT    NOT NULL DEFAULT '',       -- jieba 分词结果，空格分隔，仅供 FTS
  excerpt        TEXT    NOT NULL DEFAULT '',       -- 前 160 字纯文本，列表渲染用
  word_count     INTEGER NOT NULL DEFAULT 0,
  is_pinned      INTEGER NOT NULL DEFAULT 0,
  is_archived    INTEGER NOT NULL DEFAULT 0,
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,
  deleted_at     INTEGER
);
CREATE INDEX idx_note_updated ON note(updated_at DESC) WHERE deleted_at IS NULL;
CREATE INDEX idx_note_pinned  ON note(is_pinned DESC, updated_at DESC) WHERE deleted_at IS NULL;

-- 外部内容 FTS5 表：不复制正文，只建索引，省一半空间
CREATE VIRTUAL TABLE note_fts USING fts5(
  title,
  content_tokens,
  content      = 'note',
  content_rowid= 'rowid',
  tokenize     = "unicode61 remove_diacritics 2"
);

CREATE TRIGGER note_ai AFTER INSERT ON note BEGIN
  INSERT INTO note_fts(rowid, title, content_tokens)
  VALUES (new.rowid, new.title, new.content_tokens);
END;
CREATE TRIGGER note_ad AFTER DELETE ON note BEGIN
  INSERT INTO note_fts(note_fts, rowid, title, content_tokens)
  VALUES ('delete', old.rowid, old.title, old.content_tokens);
END;
CREATE TRIGGER note_au AFTER UPDATE ON note BEGIN
  INSERT INTO note_fts(note_fts, rowid, title, content_tokens)
  VALUES ('delete', old.rowid, old.title, old.content_tokens);
  INSERT INTO note_fts(rowid, title, content_tokens)
  VALUES (new.rowid, new.title, new.content_tokens);
END;

-- ============================== 目标 ==============================
CREATE TABLE goal (
  id              TEXT    PRIMARY KEY,
  title           TEXT    NOT NULL,
  description_md  TEXT    NOT NULL DEFAULT '',
  status          TEXT    NOT NULL DEFAULT 'active',   -- draft|active|paused|achieved|dropped
  horizon         TEXT    NOT NULL DEFAULT 'quarter',  -- week|month|quarter|year|life
  category        TEXT,
  color           TEXT,                                 -- OKLCH 字符串
  parent_id       TEXT    REFERENCES goal(id) ON DELETE SET NULL,
  progress_mode   TEXT    NOT NULL DEFAULT 'task',     -- task|kr|manual
  progress_manual REAL,                                 -- 0.0–1.0，仅 manual 模式
  start_date      TEXT,                                 -- 'YYYY-MM-DD'
  target_date     TEXT,
  achieved_at     INTEGER,
  sort_key        TEXT    NOT NULL,
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL,
  deleted_at      INTEGER
);
CREATE INDEX idx_goal_status ON goal(status, sort_key) WHERE deleted_at IS NULL;

-- 关键结果（可量化目标）
CREATE TABLE key_result (
  id            TEXT    PRIMARY KEY,
  goal_id       TEXT    NOT NULL REFERENCES goal(id) ON DELETE CASCADE,
  title         TEXT    NOT NULL,
  unit          TEXT    NOT NULL DEFAULT '',
  start_value   REAL    NOT NULL DEFAULT 0,
  target_value  REAL    NOT NULL,
  current_value REAL    NOT NULL DEFAULT 0,
  sort_key      TEXT    NOT NULL,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE INDEX idx_kr_goal ON key_result(goal_id, sort_key);

-- ============================== 待办 ==============================
CREATE TABLE task (
  id           TEXT    PRIMARY KEY,
  title        TEXT    NOT NULL,
  notes_md     TEXT    NOT NULL DEFAULT '',
  status       TEXT    NOT NULL DEFAULT 'todo',   -- todo|doing|done|cancelled
  priority     INTEGER NOT NULL DEFAULT 0,        -- 0无 1低 2中 3高 4紧急
  is_all_day   INTEGER NOT NULL DEFAULT 1,
  due_date     TEXT,                              -- 'YYYY-MM-DD'，全天任务用
  due_at       INTEGER,                           -- UTC ms，定时任务用
  remind_at    INTEGER,
  rrule        TEXT,                              -- 重复任务：完成后自动生成下一次
  completed_at INTEGER,
  goal_id      TEXT    REFERENCES goal(id) ON DELETE SET NULL,
  parent_id    TEXT    REFERENCES task(id) ON DELETE CASCADE,
  sort_key     TEXT    NOT NULL,                  -- fractional index，拖拽排序不重编号
  estimate_min INTEGER,
  actual_min   INTEGER,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER,
  CHECK (status IN ('todo','doing','done','cancelled'))
```

#### 为什么需要 `activity` 表

复盘要回答「本周完成了多少任务、分别在什么时候完成的、哪天最高产」。如果只看 `task` 表，用户把一个任务重开再完成、或改了截止日期，历史就丢了。`activity` 是 append-only 的，写入后永不修改，这样：

- 统计可回溯，历史复盘的数字不会因为后来改数据而变
- 「今日热力图」「连续打卡天数」这类特性零成本
- 出 bug 时有完整审计轨迹

同理，`review.snapshot_json` 在生成复盘时把当时的统计冻结进去 —— 三个月后回看这份周报，看到的还是当时的数字。

#### 拖拽排序：fractional indexing

`sort_key TEXT` 存的是可比较的字符串（`a0`、`a1`、`a0V`…）。把 A 拖到 B 和 C 之间，只需算 `generateKeyBetween(B.sort_key, C.sort_key)`，**只 UPDATE 一行**。用整数 `order` 字段的话，每次拖拽要重排整列 —— 100 个任务就是 100 次 UPDATE，动画必然掉帧。

```ts
import { generateKeyBetween } from 'fractional-indexing';
const newKey = generateKeyBetween(prev?.sortKey ?? null, next?.sortKey ?? null);
```

### 5.4 迁移策略

用 SQLite 内建的 `PRAGMA user_version`，不引第三方迁移框架。

```rust
// src-tauri/src/db/migrate.rs
const MIGRATIONS: &[&str] = &[
    include_str!("../../migrations/0001_init.sql"),
    // 新增迁移只能往后追加，永不修改已发布的条目
];

pub fn migrate(conn: &mut Connection) -> Result<(), AppError> {
    let current: i64 = conn.query_row("PRAGMA user_version", [], |r| r.get(0))?;
    let target = MIGRATIONS.len() as i64;

    if current > target {
        return Err(AppError::DbTooNew { found: current, supported: target });
    }
    for (i, sql) in MIGRATIONS.iter().enumerate().skip(current as usize) {
        tracing::info!("applying migration {}", i + 1);
        let tx = conn.transaction()?;
        tx.execute_batch(sql)?;
        tx.pragma_update(None, "user_version", (i + 1) as i64)?;
        tx.commit()?;
    }
    Ok(())
}
```

**规则：**
1. 迁移文件一旦发布，**永不修改**，只能追加新文件
2. 每次迁移在单个事务里完成，失败自动回滚
3. 迁移前自动做一次 SQLite Online Backup 到 `backups/pre-migration-{version}.db`
4. `DbTooNew` 分支处理降级场景：用户装了新版又退回旧版，必须明确报错而不是静默损坏数据

### 5.5 连接与并发

```rust
// src-tauri/src/db/pragma.rs
pub fn configure(conn: &Connection) -> rusqlite::Result<()> {
    conn.pragma_update(None, "journal_mode", "WAL")?;
    conn.pragma_update(None, "synchronous",  "NORMAL")?;
    conn.pragma_update(None, "foreign_keys", true)?;      // 每个连接都要设！默认是关的
    conn.pragma_update(None, "busy_timeout", 5000i64)?;
    conn.pragma_update(None, "temp_store",   "MEMORY")?;
    conn.pragma_update(None, "mmap_size",    268_435_456i64)?;

}

// src-tauri/src/state.rs
pub struct AppState {
    pub pool: Pool<SqliteConnectionManager>,
}

pub fn build_pool(path: &Path) -> Result<Pool<SqliteConnectionManager>, AppError> {
```

## 6. 中文全文搜索

### 6.1 为什么不能直接用 FTS5

- **默认 `unicode61` 分词器不切中文**：整句「今天开会讨论季度目标」会变成 1 个 token，搜「季度」完全搜不到。
- **`trigram` 分词器不够用**：它按 3 字符切分，但中文双字词（「笔记」「目标」「复盘」）极其常见，2 字查询直接无结果。

### 6.2 方案：jieba 预分词 + unicode61

写入时用 `jieba-rs` 把正文切成空格分隔的 token 串存进 `content_tokens`，FTS5 用 `unicode61` 索引这个字段。查询时同样切词。

```rust
// src-tauri/src/domain/search.rs
use jieba_rs::Jieba;
use once_cell::sync::Lazy;

static JIEBA: Lazy<Jieba> = Lazy::new(Jieba::new);   // 首次初始化 ~50ms，进程内只做一次

/// 写入索引：cut_for_search 产生细粒度重叠切分，召回率更高
/// 「季度目标」→ ["季度", "目标", "季度目标"]
pub fn tokenize_for_index(text: &str) -> String {
    JIEBA
        .cut_for_search(text, true)
        .into_iter()
        .filter(|t| !t.trim().is_empty())
        .collect::<Vec<_>>()
        .join(" ")
}

/// 查询：切词 + 前缀通配（兼顾单字查询）+ 隐式 AND
pub fn build_match_query(q: &str) -> String {
    JIEBA
        .cut_for_search(q, true)
        .into_iter()
        .map(|t| t.trim())
        .filter(|t| !t.is_empty())
        .map(|t| format!("\"{}\"*", t.replace('"', "\"\"")))  // 转义双引号，防注入
        .collect::<Vec<_>>()
        .join(" ")
}
```

`cut_for_search` 是关键：它输出重叠的细粒度切分，「季度目标」既产生 `季度目标` 也产生 `季度`、`目标`，无论用户搜整词还是搜子词都能命中。

前缀通配 `*` 解决单字查询：搜「笔」会变成 `"笔"*`，能命中 `笔记`、`笔试`。

### 6.3 查询 SQL

```sql
SELECT
  n.id, n.title, n.excerpt, n.updated_at,
  bm25(note_fts, 10.0, 1.0) AS score      -- title 权重 10x
FROM note_fts
JOIN note n ON n.rowid = note_fts.rowid
WHERE note_fts MATCH ?1
  AND n.deleted_at IS NULL
  AND n.is_archived = 0
ORDER BY score                             -- bm25 越负越相关，升序即最佳优先
LIMIT ?2;
```

### 6.4 高亮的坑

**不要用 SQLite 的 `snippet()` / `highlight()`。** 它们作用在 `content_tokens` 上，返回的是分词后的空格分隔文本 —— 中文看起来会像「今天 开会 讨论 季度 目标」，很丑。

正确做法：SQL 只负责**找到哪些笔记命中**，高亮在前端做 —— 拿分词后的 query token 列表，在原始 `content_md` 上做匹配并包裹 `<mark>`。Rust 侧把 token 列表一起返回给前端：

```rust
#[derive(Serialize, specta::Type)]
pub struct SearchResult {
    pub hits: Vec<NoteHit>,
    pub tokens: Vec<String>,   // 前端用它做高亮
}
```

### 6.5 索引重建

分词逻辑改动（升级 jieba、加自定义词典）后需要全量重建：

```sql
INSERT INTO note_fts(note_fts) VALUES('rebuild');
```

重建前必须先用新分词器刷新所有 `note.content_tokens`。这个操作在后台线程跑，UI 显示进度条。1 万篇笔记约 3–8 秒。

### 6.6 性能与降级

| 数据量 | 预期查询耗时 |
|---|---|
| 1,000 篇 | < 5 ms |
| 10,000 篇 | < 25 ms |
| 100,000 篇 | < 120 ms |

超过 10 万篇且用户抱怨搜索质量，再考虑换 **Tantivy + lindera**（Rust 原生搜索引擎，中文分词质量和排序更好）。但那是一个独立索引文件 + 一致性维护的成本，v1 不做。

## 8. 前端架构

### 8.1 状态三层

| 层 | 工具 | 内容 | 更新时机 |
|---|---|---|---|
| 服务端状态 | TanStack Query | 所有来自 SQLite 的数据 | mutation 后精确失效 |
| UI 状态 | Zustand | 侧栏开合、当前选中、拖拽中、命令面板开关 | 同步，立即 |
| 编辑器状态 | Milkdown 内部 | 文档 AST、光标、选区 | 组件内，防抖持久化 |

**不要把编辑器内容放进 React state。** ProseMirror 有自己的文档模型，每次 keystroke 都同步到 React 会导致每个字符触发一次全量重渲染 —— 打字直接卡。用 listener 插件 + 防抖，只在需要持久化时取内容。

### 8.2 Query Key 约定

集中管理，避免失效范围写错（写宽了浪费、写窄了数据不刷新）：

```ts
// src/lib/query-keys.ts
export const qk = {
  note: {
    all:    ['note'] as const,
    list:   (f: NoteFilter) => ['note', 'list', f] as const,
    detail: (id: string)    => ['note', 'detail', id] as const,
  },
  task: {
    all:    ['task'] as const,
    list:   (f: TaskFilter) => ['task', 'list', f] as const,
  },
  calendar: {
    all:   ['calendar'] as const,
    range: (from: string, to: string) => ['calendar', 'range', from, to] as const,
  },
  review: {
    stats: (p: Period, s: string) => ['review', 'stats', p, s] as const,
  },
} as const;
```

**跨模块失效规则**（这是「整合」带来的必然复杂度，必须写清楚）：

| 操作 | 需要失效的 key |
|---|---|
| 完成一个任务 | `task.all`、`goal.all`（进度变了）、`review.stats`（统计变了） |
| 修改事件时间 | `calendar.all`、若 `task_id` 非空则 `task.all` |
| 编辑笔记 | `note.detail(id)`、`note.list`；若正文里的 `[[链接]]` 有变动则 `link` 相关 |

建议为这类联动写一个 `invalidators.ts`，一处定义、各 mutation 复用。

### 8.3 乐观更新模板

```ts
// src/modules/task/api.ts
export function useCompleteTask() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: ({ id, done }: { id: string; done: boolean }) =>
      commands.taskComplete(id, done),

    onMutate: async ({ id, done }) => {
      await qc.cancelQueries({ queryKey: qk.task.all });
      const snapshot = qc.getQueriesData({ queryKey: qk.task.all });
      qc.setQueriesData({ queryKey: qk.task.all }, (old: Task[] | undefined) =>
        old?.map(t => t.id === id
          ? { ...t, status: done ? 'done' : 'todo', completedAt: done ? Date.now() : null }
          : t));
      return { snapshot };
    },

    onError: (_e, _v, ctx) => {
      ctx?.snapshot.forEach(([key, data]) => qc.setQueryData(key, data));
    },

    onSettled: () => {
      qc.invalidateQueries({ queryKey: qk.task.all });
      qc.invalidateQueries({ queryKey: qk.goal.all });
    },
  });
}
```

## 10. 动效规范

> 参考 Telegram 的核心不是「动画多」，而是「每个动画都短、都可打断、都不掉帧」。

### 10.1 三条铁律

**① 只动 `transform` 和 `opacity`。**

这两个属性由合成线程独立处理，主线程再忙也不掉帧。动 `width/height/top/left/margin/padding` 会触发每帧重排（layout），必然掉帧。

需要「宽度动画」时，用 `transform: scaleX()` + 内部反向 scale 补偿，或用 Motion 的 `layout` 属性（它内部就是把 layout 变化转译成 transform）。

**② 绝不动画化 `backdrop-filter` 和 `box-shadow`。**

毛玻璃面板是 Telegram 风格的重要部分，但 `backdrop-filter` 每帧都要重新采样背景做模糊，代价极高。规则：
- 毛玻璃**静态使用**没问题
- 要让毛玻璃面板「淡入」，做法是：预先渲染好带 `backdrop-filter` 的层，只动画它的 `opacity`
- 阴影渐变同理：两个不同阴影的伪元素做 opacity 交叉淡入，不要动画 `box-shadow` 本身

**③ 动画时长 120–320ms，且必须可打断。**

生产力工具里 400ms 的转场用三天就会烦。Telegram 的动画之所以不烦，正是因为短到你意识不到。Motion 的 spring 天然可打断（新目标值会从当前速度接管），而 CSS transition 不行 —— 这是优先用 Motion 而非 CSS 的主要原因。

### 10.2 Spring 预设

```ts
// src/lib/motion-tokens.ts
import type { Transition } from 'motion/react';

export const spring = {
  /** 按钮、勾选、开关 —— 快、几乎不回弹 */
  snappy: { type: 'spring', stiffness: 520, damping: 34, mass: 0.7 },
  /** 列表重排、卡片位移 —— 默认选择 */
  smooth: { type: 'spring', stiffness: 320, damping: 30 },
  /** 面板滑入、大块内容 */
  gentle: { type: 'spring', stiffness: 190, damping: 26 },
  /** 强调：新建成功、完成任务 —— 少用 */
  bouncy: { type: 'spring', stiffness: 420, damping: 17 },
} satisfies Record<string, Transition>;

export const tween = {
  fast: { duration: 0.14, ease: [0.22, 1, 0.36, 1] },
  base: { duration: 0.22, ease: [0.22, 1, 0.36, 1] },
} satisfies Record<string, Transition>;

/** 列表入场错峰。上限 8 项，否则第 20 项要等 400ms 才出现 */
export const stagger = (i: number) => ({ delay: Math.min(i, 8) * 0.028 });
```

### 10.3 场景对照表

| 场景 | 技术 | 参数 | 备注 |
|---|---|---|---|
| 主视图切换（笔记↔日历） | View Transitions API | 220ms `ease-out-quint` | 交叉淡入 + 轻微 scale(0.98→1) |
| 笔记列表 → 详情 | Motion `layoutId` | `spring.smooth` | 共享元素：标题从卡片飞到标题栏 |
| 侧栏折叠 | Motion `animate` on `x` | `spring.gentle` | 不动 `width`，动 `x` + 内容 opacity |
| 任务勾选 | Motion + SVG `pathLength` | `spring.snappy` | 对勾描边 + 文字划线 + 整行淡出 |
| 任务拖拽排序 | dnd-kit + Motion `layout` | `spring.smooth` | 拖起时 `scale(1.02)` + 阴影层 opacity |
| 弹窗 / 命令面板 | Motion `AnimatePresence` | `spring.snappy` | `opacity 0→1` + `scale 0.96→1` + `y 8→0` |
| Toast | `AnimatePresence` + `layout` | `spring.smooth` | 多条堆叠时自动重排 |
| 日历月份切换 | Motion `AnimatePresence` `mode="popLayout"` | `tween.base` | 方向感知：下一月从右滑入 |
| 空状态插画 | Rive | 状态机驱动 | 见下 |
| 目标进度环 | SVG `strokeDashoffset` + Motion | `spring.gentle` | 数字用 `useSpring` + `useTransform` 滚动 |
| 复盘热力图 | 单个 `<canvas>` | 无入场动画 | 365 个格子，DOM 方案会卡；hover 高亮走 canvas 重绘 |
| 悬停反馈 | 纯 CSS `transition` | 80ms | 这种极短的用 CSS 更省，不必上 Motion |

### 10.4 复杂矢量动画：Rive 优先

需要设计师产出的复杂动画（空状态插画、加载动画、成就徽章）：

- **首选 Rive**（`@rive-app/react-canvas`）—— GPU 渲染 + 状态机，一个文件几十 KB，运行时开销远低于 Lottie
- **退路 dotLottie**（`@lottiefiles/dotlottie-web`）—— 如果设计师只能给 Lottie 文件。必须用 wasm 版，它在独立线程渲染；**不要用 `lottie-web`**，它在主线程逐帧操作 DOM/SVG，一个复杂动画就能吃掉整个帧预算

### 10.5 无障碍与降级

```ts
// 全局降级开关：系统设置 OR 应用内设置
export function useMotionEnabled() {
  const userPref = useSettings(s => s.reduceMotion);
  const systemPref = useMediaQuery('(prefers-reduced-motion: reduce)');
  return !userPref && !systemPref;
}
```

在 Motion 的 `MotionConfig` 上统一设置 `reducedMotion="user"`，所有子组件自动降级为瞬时变化。**同时提供应用内开关** —— 有些用户系统没开但就是不想要动效。

### 10.6 `will-change` 纪律

```css
/* ❌ 错误：常驻 will-change 会为每个元素永久分配合成层，显存爆炸 */
.card { will-change: transform; }

/* ✅ 正确：只在交互瞬间提升 */
.card:hover,
.card[data-dragging="true"] { will-change: transform; }
```

Motion 会自动管理这个属性，手写 CSS 动画时要自己注意。

## 11. 编辑器集成（Milkdown）

### 11.1 为什么是 Milkdown

Milkdown 的底层是 **ProseMirror + remark**。remark 是 Markdown AST 的事实标准，这意味着「Markdown 字符串 → AST → 编辑 → AST → Markdown 字符串」的往返几乎无损。Tiptap 虽然生态更大，但它的 Markdown 序列化是外挂的，表格、嵌套列表、脚注这些结构往返几次就会变形。

因为我们把 Markdown 当作**存储格式**（不是导出格式），保真度是第一位的。

### 11.2 集成方式

v1 直接用 **Crepe**（Milkdown 官方的开箱即用编辑器，自带斜杠菜单、工具条、表格、图片、代码高亮），后续按需 eject 到底层 API 自定义。

```tsx
// src/editor/MarkdownEditor.tsx
import { Crepe } from '@milkdown/crepe';
import '@milkdown/crepe/theme/common/style.css';
import { useEffect, useRef } from 'react';

interface Props {
  initial: string;
  onChange: (md: string) => void;   // 已在外层防抖
}

export function MarkdownEditor({ initial, onChange }: Props) {
  const host = useRef<HTMLDivElement>(null);
  const composing = useRef(false);
  const onChangeRef = useRef(onChange);
  onChangeRef.current = onChange;

  useEffect(() => {
    if (!host.current) return;
    const crepe = new Crepe({
      root: host.current,
      defaultValue: initial,
    });

    crepe.on(listener => {
      listener.markdownUpdated((_ctx, md) => {
        // ★ 中文输入法组合期间不触发上层更新
        if (composing.current) return;
        onChangeRef.current(md);
      });
    });

    crepe.create();
    return () => { crepe.destroy(); };
    // ★ 依赖数组故意只有 initial：Crepe 是命令式实例，不能跟着 props 重建
  }, [initial]);

  return (
    <div
      ref={host}
      className="markdown-body"
      onCompositionStart={() => { composing.current = true; }}
      onCompositionEnd={()   => { composing.current = false; }}
    />
  );
}
```

### 11.3 四个必须遵守的约定

**① IME 组合期间不做任何上层状态更新。**

中文输入时，`compositionstart` 到 `compositionend` 之间会持续触发 input 事件。这期间如果触发 React 重渲染或持久化，轻则卡顿，重则**吞字、候选框错位**。上面的 `composing` ref 就是为此。这是中文用户会立刻感知的问题，优先级最高。

**② 编辑器容器必须是动画的「稳定岛」。**

ProseMirror 依赖 `getBoundingClientRect` 定位光标、选区、悬浮工具条。如果编辑器的祖先容器正在跑 Motion `layout` 动画（不断改 transform），这些测量全部错位 —— 光标会飘、工具条会跑偏。

**规则：编辑器所在的容器及其所有祖先，不得应用 `layout` / `layoutId` 动画。** 需要「详情页飞入」效果时，让容器先完成动画，动画结束后（`onAnimationComplete`）再挂载编辑器；或者动画期间显示只读的 Markdown 渲染结果，动画完成后再切成编辑器。

**③ 持久化：防抖 400ms + 关键时刻强制 flush。**

```ts
const flush = useRef<() => void>();
const debouncedSave = useMemo(
  () => debounce((md: string) => save(md), 400),
  []
);
// 必须强制 flush 的时机：切换笔记、关闭窗口、切路由、失焦、Cmd+S
useEffect(() => () => debouncedSave.flush(), []);
```

Tauri 侧监听窗口关闭事件，给前端一个 flush 的机会（`onCloseRequested` + `preventDefault` + 保存后 `close()`）。

**④ 大文档降级。**

ProseMirror 在超过 ~50KB 正文（约 2.5 万汉字）后编辑会明显变慢。处理策略：

- 打开笔记时先检查 `word_count`
- 超过阈值 → 默认渲染为**只读 Markdown 预览**（Web Worker 里解析），顶部提示「文档较大，点击进入编辑模式」
- 用户主动点击才实例化 Milkdown

配合 `content-visibility: auto` 让屏幕外的段落跳过渲染。

### 11.4 自定义插件

| 插件 | 用途 | 实现 |
|---|---|---|
| 双链 `[[...]]` | 引用其他笔记 / 任务 / 目标 | ProseMirror InputRule + 自定义 Node + 弹出搜索面板；保存时同步写 `link` 表 |
| 任务勾选块 | 笔记里的 `- [ ]` 双向关联真实 task | 自定义 Node，勾选直接调 `task_complete` |
| 日期引用 `@2026-08-29` | 点击跳到日历 | InputRule + Mark |
| 图片粘贴 | 存到 app data 的 `assets/`，正文写相对路径 | 拦截 paste，Tauri 侧写文件，返回路径 |

## 12. 各模块设计

### 12.1 笔记

- **列表**：TanStack Virtual 虚拟化，列表项只用 `excerpt`（不查 `content_md`），滚动稳定
- **详情**：`note_get` 单独取全文
- **组织**：不做文件夹树，用**标签 + 双向链接 + 搜索**（文件夹在个人笔记场景里往往是负担）
- **入场动画**：列表项 stagger 28ms/项，上限 8 项；点击卡片用 `layoutId` 把标题飞到详情标题栏

### 12.2 待办

- **视图**：今天 / 本周 / 收件箱 / 按目标 / 日历（时间块）
- **排序**：fractional index，dnd-kit 拖拽 + Motion `layout` 补间
- **重复任务**：完成时，Rust 侧按 `rrule` 算出下一次 due 并创建新行（不是复用同一行）。保留每一次的独立记录，复盘统计才有意义
- **完成动画**：SVG 对勾 `pathLength: 0→1`（`spring.snappy`）→ 文字 `text-decoration` 划线 → 200ms 后整行 `layout` 淡出移到「已完成」区。三段串联，总时长 < 450ms

### 12.3 目标

- **层级**：`parent_id` 支持 2–3 层（年度目标 → 季度目标 → 月度目标）
- **进度三模式**：
  - `task`：子任务完成数 / 总数
  - `kr`：各 key result 的 `(current - start) / (target - start)` 平均
  - `manual`：用户手动拖进度条
- **进度环**：SVG `circle` + `strokeDashoffset`，用 Motion 的 `useSpring` 驱动；中心数字用 `useTransform` 做滚动数字效果
- **与任务的联动**：任务完成 → 失效 `goal.all` → 进度环 spring 动画到新值（这里必须用 spring 而非 tween，因为可能连续多次完成任务，spring 能从当前速度平滑接管）

### 12.4 日历

- **视图**：月 / 周 / 日 / 议程，全部自己用 CSS Grid 画
  - 不用 FullCalendar：太重（~300KB）、样式难改、动画完全无法接管
- **数据**：只调 `event_range(from, to, tz)`，拿到扁平的 occurrence 列表。前端不碰 rrule
- **预取**：当前月份两侧各预取一个月（`prefetchQuery`），切月时数据已在缓存，动画不等待
- **时间块**：把 task 拖到日历上 → 创建带 `task_id` 的 event。这是「待办 ↔ 日历」的整合点
- **重复事件编辑**：修改时弹窗询问作用域（仅此次 / 此次及以后 / 全部），对应 `event_update_occurrence` 的 `scope` 参数。这是日历功能里最容易做错的一块，必须在 Rust 侧集中实现，有完整单测
- **动画**：月份切换用 `AnimatePresence mode="popLayout"`，方向感知（下月从右、上月从左）。事件块入场只做 opacity，**不做 stagger** —— 一个月可能有 60 个事件，stagger 会拖出长尾

### 12.5 复盘

- **周期**：日 / 周 / 月 / 季 / 年
- **统计来源**：全部从 `activity` 表聚合，不从 `task`/`note` 现状读
- **生成流程**：
  1. `review_stats(period, start, tz)` → Rust 聚合出 `ReviewStats`
  2. 前端渲染统计卡片 + 一个 Markdown 编辑器（用户写主观复盘）
  3. 首次保存时把 `ReviewStats` 序列化进 `review.snapshot_json` **冻结**
  4. 之后再打开这份复盘，读 `snapshot_json` 而非重新聚合
- **统计内容**：完成任务数、按目标分布、笔记产出字数、日历时间分配、连续打卡、心情/精力曲线
- **可视化**：
  - 热力图（365 格）→ **canvas**，DOM 方案在 hover 时会卡
  - 折线/柱状 → 手写 SVG（数据点少，不值得引图表库）
  - 目标完成度 → 复用进度环组件
- **模板**：复盘正文提供可配置的 Markdown 模板（做得好的 / 没做好的 / 下周计划），存在 `setting` 表

## 13. 性能预算与红线

### 13.1 量化目标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 冷启动到可交互 | < 800 ms | Tauri `setup` 开始到首帧 paint |
| 视图切换 | < 100 ms 首帧 | Performance API |
| 帧率 | 稳定 60 fps（120Hz 屏 120fps） | DevTools Performance，无 dropped frame |
| 长任务 | 主线程无 > 50 ms 任务 | Long Task API |
| 搜索响应（1 万篇） | < 30 ms | Rust 侧 tracing 埋点 |
| 常驻内存 | < 150 MB | 任务管理器 / Activity Monitor |
| 安装包 | < 20 MB | 打包产物 |
| 数据库（1 万笔记） | < 80 MB | 文件大小 |

### 13.2 保障手段

| 手段 | 说明 |
|---|---|
| 长列表虚拟化 | 超过 50 项一律 TanStack Virtual |
| 屏幕外跳过渲染 | `content-visibility: auto` + `contain-intrinsic-size` |
| 重计算移到 Rust | 分词、搜索、rrule 展开、统计聚合、导出 |
| 中等计算移到 Worker | 大文档 Markdown 预览渲染 |
| 图片资源 | 存本地文件，用 `convertFileSrc()` 引用；不做 base64 内联（会撑爆内存） |
| 启动优化 | 路由级 `React.lazy`；首屏只加载笔记模块；日历/复盘按需加载 |
| jieba 预热 | Tauri `setup` 里异步初始化 `JIEBA`（首次 ~50ms），别等到用户第一次搜索 |
| 数据库预热 | 启动时异步跑一次轻量查询，让 SQLite 建立页缓存 |

### 13.3 性能回归防线

在 CI 里加一条：用 Playwright 跑一个「打开 1000 篇笔记的库 → 滚动列表 → 切换视图」的脚本，采集帧数据，dropped frame > 3% 就 fail。

没有这条防线，动画性能一定会随着功能增加缓慢劣化，而且发现时已经很难定位。

## 14. 构建与发布

### 14.1 Rust Release 配置

```toml
# src-tauri/Cargo.toml
[profile.release]
opt-level     = "s"      # 优化体积；如果发现运行时慢，改 "z"→"s"→3 逐级测
lto           = true
codegen-units = 1
panic         = "abort"
strip         = true
incremental   = false
```

> `panic = "abort"` 能显著减小体积，但会让 panic 直接终止进程而非 unwind。Tauri 本身兼容，但如果引入了依赖 catch_unwind 的库需要去掉这行。发布前用真实场景验证一遍崩溃行为。

### 14.2 打包目标

```jsonc
// src-tauri/tauri.conf.json（节选）
{
  "bundle": {
    "active": true,
    "targets": ["nsis", "dmg", "appimage", "deb"],
    "windows": {
      "nsis": { "installMode": "perMachine", "languages": ["SimpChinese", "English"] },
      "webviewInstallMode": { "type": "downloadBootstrapper" }
    },
    "macOS": { "minimumSystemVersion": "13.0" }
  },
  "plugins": {
    "updater": {
      "endpoints": ["https://<你的更新源>/latest.json"],
      "pubkey": "<tauri signer generate 产出的公钥>"
    }
  }
}
```

Windows 上 WebView2 用 `downloadBootstrapper`（~2MB 引导程序，需要时才下载完整运行时）。Windows 11 已预装，实际很少触发下载。

### 14.3 自动更新

```bash
pnpm tauri signer generate -w ~/.tauri/ontheway.key
```

私钥进 CI secret（`TAURI_SIGNING_PRIVATE_KEY`），公钥写进 `tauri.conf.json`。更新源用 GitHub Releases 托管的静态 `latest.json` 即可，零成本。

### 14.4 代码签名（必须提前规划成本）

| 平台 | 要求 | 不签的后果 | 年成本 |
|---|---|---|---|
| Windows | OV/EV 代码签名证书 | SmartScreen 拦截，显示「未知发布者」，用户需点两次「仍要运行」 | ~$200–400 |
| macOS | Apple Developer ID + 公证 | Gatekeeper 直接拒绝，用户必须去系统设置手动放行 | $99 |
| Linux | 无 | 无 | 0 |

**建议：** 个人自用或小范围分发可以先不签，但要在下载页写清楚放行步骤。一旦想公开分发，macOS 的 $99 是必须的（Gatekeeper 的拦截强度远高于 SmartScreen）。

### 14.5 数据备份

- 每日首次启动时用 SQLite Online Backup API 备份到 `backups/ontheway-YYYY-MM-DD.db`
- 保留最近 7 份 + 每月 1 份，共约 19 份
- 迁移前强制额外备份一份
- 设置页提供「立即备份」「打开备份文件夹」「从备份恢复」

## 15. 测试策略

| 层级 | 工具 | 覆盖范围 | 优先级 |
|---|---|---|---|
| Rust 单元测试 | `cargo test` + `:memory:` SQLite | **domain/ 全部**：rrule 展开、进度计算、分词、统计聚合、fractional index | ★★★ |
| Rust 集成测试 | `cargo test` + 临时库文件 | 迁移链路（从 v1 逐级迁到最新）、备份恢复 | ★★★ |
| 前端单元 | Vitest | 日期工具、query key、乐观更新 reducer | ★★ |
| 组件测试 | Vitest + Testing Library | 表单校验、键盘交互 | ★ |
| E2E | Playwright + `tauri-driver` | 主流程冒烟 | ★★ |
| 性能回归 | Playwright + trace | 见 [13.3](#133-性能回归防线) | ★★ |

**必须有单测的三块（错了用户会立刻发现且信任崩塌）：**

1. **rrule 展开**：跨夏令时、跨年、`BYSETPOS`、EXDATE、override 的组合
2. **时区转换**：全天事件跨时区、定时事件跨 DST
3. **迁移链路**：从每一个历史版本迁到最新都能成功

> **E2E 的限制**：`tauri-driver` 只支持 Windows 和 Linux（macOS 的 WKWebView 没有 WebDriver 实现）。macOS 上的 E2E 只能靠手动冒烟测试。这是 Tauri 相对 Electron 唯一实打实的劣势，接受它。

## 16. 开发路线图

按「数据模型稳定优先」排序。复盘必须放最后 —— 它是前四者的聚合视图，前面的模型不稳时做复盘等于返工。

| 阶段 | 内容 | 交付标准 |
|---|---|---|
| **M0 地基**<br>1–2 周 | Tauri 脚手架、SQLite + 迁移、tauri-specta 打通、design token、动效 token、`ui/primitives` 基础组件、应用外壳（侧栏 + 标题栏 + 命令面板） | 能跑起来，切换空视图有 View Transition 动画 |
| **M1 笔记**<br>2–3 周 | Milkdown 集成（含 IME 处理）、笔记 CRUD、虚拟化列表、jieba 搜索、标签 | 能当一个可用的 Markdown 笔记本 |
| **M2 待办**<br>2 周 | 任务 CRUD、多视图筛选、dnd-kit 拖拽排序、重复任务、完成动画、提醒调度器 | 能替代现有 todo 工具 |
| **M3 日历**<br>2–3 周 | 月/周/日视图、rrule 展开、override 编辑作用域、任务时间块 | 重复事件的三种编辑作用域全部正确 |
| **M4 目标**<br>1–2 周 | 目标层级、KR、三种进度模式、进度环动画、与任务联动 | 完成任务时目标进度环平滑更新 |
| **M5 复盘**<br>2 周 | activity 聚合、快照冻结、热力图、图表、模板 | 生成的周报数字与手工核对一致 |
| **M6 打磨**<br>持续 | 全局搜索、双向链接面板、导出 Markdown、性能回归 CI、代码签名、自动更新 | 达到 [13.1](#131-量化目标) 全部指标 |

**贯穿全程：** 动效规范从 M0 就定死并写进 token。不要等到 M6 再统一动画风格 —— 那时候要改的地方是分散在几十个组件里的魔法数字。

## 17. 风险登记

| # | 风险 | 影响 | 概率 | 应对 |
|---|---|---|---|---|
| 1 | **Linux WebKitGTK 动画卡顿** | Linux 用户体验明显差 | 高 | 明确 Linux 为二等公民；检测到 WebKitGTK 时自动降级动效（关闭 layout 动画和毛玻璃）；实在不行为 Linux 单独出 Electron 构建 |
| 2 | **中文 IME 在编辑器里吞字/卡顿** | 核心体验崩塌 | 中 | composition 门控（[11.3](#113-四个必须遵守的约定)）；M1 阶段就在 Windows 微软拼音 / macOS 原生拼音上做专项测试，不要等到后期 |
| 3 | **jieba 分词质量不足**（专业术语、人名切错） | 搜不到 | 中 | 支持用户自定义词典（`jieba.add_word`）；提供「精确匹配」模式绕过分词走 `LIKE` |
| 4 | **rrule 边界情况出错** | 日历显示错误，信任崩塌 | 中 | 集中在 Rust 单一模块实现；用 RFC 5545 官方示例做测试集；夏令时场景专项测试 |
| 5 | **Milkdown 大文档卡顿** | 长笔记不可用 | 中 | 阈值降级为只读预览（[11.3](#113-四个必须遵守的约定)）；引导用户拆分长笔记 |
| 6 | **范围蔓延** | 永远发不出 v1 | **高** | 严格按 M0–M5 顺序；每个阶段结束必须能独立使用；[1.3](#13-明确不做v1) 的清单不松口 |
| 7 | **动画过度导致「慢」的错觉** | 效率工具变得低效 | 中 | 时长上限 320ms 写进 lint 规则；提供「减少动效」开关；每个阶段做一次「快速操作 20 次」的手感自测 |
| 8 | **tauri-specta 处于 RC 阶段** | 升级可能 break | 低 | 生成物是纯 TS 文件，最坏情况手写类型；锁定版本，不自动升级 |
| 9 | **macOS 无法跑 E2E** | 回归靠手测 | 中 | 维护一份 macOS 手动冒烟清单；Rust 层测试覆盖率拉高，把逻辑错误挡在前端之前 |
